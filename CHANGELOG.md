## 1.0.8.0 (unreleased)

- Fixed Format Compatibility scanner silently missing all 10 unindexed ebook formats (TXT, RTF, DOC, DOCX, FB2, LIT, LRF, PDB, HTMLZ, CHM). Jellyfin's book resolver never creates `BaseItem`s for these extensions, so the existing item-loop walk never saw them — users were never told they could be converted to EPUB. A second filesystem-sweep pass now walks library folder trees for any extension the matrix marks `ServerIndexes=false`, emitting issues with `ItemId=Guid.Empty` and `unindexed:true` in the DetailsJson. `FormatCompatibilityScanner` also now sets `AlwaysUnscoped=true` (same reason as `SuspiciousFileScanner`). `FormatCompatibilityFixer` gains a one-line null-item fallback that reads `libraryKind` from the frozen DetailsJson so unindexed files in named libraries aren't mis-gated as mixed-library requiring manual approval. (external code review P2-5)
- Fixed three P1 safety bugs in `FormatCompatibilityFixer`: (1) `checkCurrentPolicy` callback now re-reads live config + `ProtectionService` at commit time instead of always returning Allow, so a mid-conversion dry-run flip, fixer disable, per-kind toggle off, or protection addition aborts before any file is touched; (2) source length and mtime are now captured before `ConvertAsync` runs, not after, so a source file mutated during a long Calibre conversion is correctly detected as changed and the stale encode is discarded; (3) `VerifyOutputAsync` now dispatches to `BookProbeService.Probe` (EPUB/PDF/MOBI/DjVu) and `ComicProbeService.Probe` (CBZ/CBR/CB7) before committing, so an unreadable or truncated converted output is refused before the original is disposed. (external code review P1-1 / P1-2 / P1-3)
- Hardened Format Compatibility (Phase 2.5). Calibre auto-download now actually extracts: `CalibreToolchain` shells out `cmd /C <installer> <extractRoot>` (Calibre's portable installer needs a console attached — silent extract flags alone open a GUI folder picker), then resolves `Calibre Portable\Calibre\ebook-convert.exe` inside the extracted tree and cleans up the 200 MB installer. `POST /Issues/{id}/Approve` now patches `approvedInMixedLibrary: true` into the FormatCompatibility issue's DetailsJson so the fixer honors user approval in truly-mixed libraries. `LibraryCollectionResolver` appends a directory separator before the path-prefix compare so items under `C:\media\books_extended` no longer false-positive-match a `C:\media\books` library. Also replaces the stub CBR test fixture with a real 3-image RAR built via WinRAR, clearing the last known test failure. (F-format-compat)
- Added end-to-end Format Compatibility conversion (Phase 2). `EbookConverter` shells out to Calibre's `ebook-convert` (handles MOBI/AZW/AZW3/DjVu plus TXT/RTF/DOC/DOCX/FB2/LIT/LRF/PDB/HTMLZ/CHM). `ComicConverter` repacks CBR/CB7 → CBZ via SharpCompress (no external tool). `FormatCompatibilityFixer` dispatches to the right converter, enforces the library-type gate and mixed-library "user approval only" rule, then hands the staged output to `VerifiedReplacementService` for the audited swap-and-recycle protocol. `CalibreDownloader` lazily fetches the Calibre 9.15.0 portable installer from calibre-ebook.com on first fix (Windows only; Linux/macOS still resolve via `PATH` or `CalibreOverridePath`), SHA-256-verified. New Settings section (`Format conversion`) exposes fix mode, disposal, per-kind toggles (`ConvertEbooks`, `ConvertComics`), and the override path. Also fixes `LibraryCollectionResolver` — Book items on Jellyfin 10.11 don't have their `CollectionFolder` in `GetTopParent()`, so the resolver now does a path-prefix lookup against `ILibraryManager.GetVirtualFolders()` — and adds `FormatCompatibility` to `FixTask.FixableTypes` so `FixMode.Automatic` actually auto-queues it. Verified end-to-end on the dev Jellyfin at localhost:8099: real MOBI → EPUB conversion with the source recycled. (F-format-compat)
- Added scan-only Format Compatibility feature scaffold (Phase 1): matrix + scanner + Calibre toolchain stub. Detects files in formats Jellyfin's browser can't render (MOBI, CBR, HEIC, tracker files, etc.). Conversion arrives in Phase 2. (F-format-compat)
- Fixed Never-modify protection failing to match when a rule was stored with forward slashes or dot segments (`C:/dev/Foo`, `C:\dev\.\Foo`) — `ProtectionService.PathIsUnder` handled alt-separators only on the incoming path, and `MediaDashController.CreateProtection` stored the target through `Path.TrimEndingDirectorySeparator` which does not normalise internal separators or resolve `\.\` segments. A rule created for such a path silently protected nothing, so scans and fixes ran against files inside the "protected" folder anyway. Both sides now canonicalise through `Path.GetFullPath` — store-side rejects invalid paths with a clear 400, compare-side collapses any pre-existing bad rules at match time so already-persisted rules also start working without a migration. (external audit finding P1-F1, roadmap i-110-protected-media)
- Fixed `POST /MediaDash/Files/Delete` ignoring Never-modify protection — the endpoint validated library containment but never consulted `ProtectionService`, so a manual recycle from the Files tab succeeded on a path under an `All` (or `ManualDelete`-masked) rule. This contradicted the Settings promise that protected paths are not modified, and `ManualDelete` was even offered in the protectable-issue-types dropdown. `FileBrowserController` now injects `ProtectionService` and refuses with 403 before any recycle-bin write. Applies uniformly to file and directory deletes. (external audit finding P1-F2, roadmap i-110-protected-media)
- Fixed protection added during a long re-encode being ignored at the swap. `TranscodeFixer` re-reads config at commit time for the F-206 dry-run gate but did not consult `ProtectionService`, so a rule added between plan build and commit (a several-hour 4K→1080p encode gives a wide window) let the source file get replaced anyway. `checkCurrentPolicy` now also refuses on `_protection.IsFixerBlocked(issue.Path, issue.Type)` with `FixReason.Protected` — the source is preserved, the encode is discarded, and the queued issue stays visible so removing the rule later resumes it. (external audit finding P1-F3, roadmap i-110-protected-media)
- Fixed Quality re-encodes with `Failed+InsufficientSavings` being retried on every rescan. `FixResultPolicy` correctly maps the outcome to `CompleteLegacy` (queue disposition), but the scanner's re-insert `NOT EXISTS` clause only suppresses on `Queued`/`Dismissed`, and `RecordFixOutcome` transitioned the primary Queued→Fixed. Next scan re-detected → auto-queue → re-encode → same deterministic failure → loop, wasting CPU on every scheduled scan. `FixResultRecorder` now promotes the primary Fixed→Dismissed when the outcome is `Failed+InsufficientSavings` on a real (non-dry-run) attempt so the existing suppression path closes the loop. User can un-dismiss via the Issues tab if they lower the savings threshold and want to retry. (external audit finding P2-F4, roadmap i-110-minimum-savings)
- Hardened `POST /MediaDash/Protection` against ineffective rules. Unknown `IssueType` names in `ScannersMask` / `FixersMask` (e.g. `NotARealIssue`) and unresolved `library`-kind targets both persisted successfully and silently protected nothing. `CreateProtection` now parses every mask token through `Enum.TryParse<IssueType>` (accepting `*` verbatim) and resolves library targets against `VirtualFolderIdentity.BuildIdLookup(_libraryManager)`; unknown tokens or unknown library ids return 400 with an actionable message. (external audit finding P2-F5, roadmap i-110-protected-media)
- Fixed the Issues tab audio-language filter dropdown (`#mdIssueLangFilter`) rendering with un-themed default browser colors in light mode. The `<select>` was missing the `emby-select-withcolor emby-select` class every other MediaDash-emitted select carries, so Jellyfin's theme engine wasn't applying its usual foreground/background rules to it and the option list looked visually broken against a light theme. One-line class addition brings it in line with the wizard + settings selects.
- Overview now surfaces a "Broken files repaired" panel showing files rescued by the Playability repair ladder (30-day + lifetime counts, bytes rescued from deletion, per-rung breakdown across quick remux / dropped broken streams / container coerce / audio re-encoded / video re-encoded). Powered by a new `Api/RepairSummary` DTO plus a schema v9 migration adding `history.saved_bytes` — the `FixResult.SavedBytes` / `HistoryEntry.SavedBytes` properties existed before this build but were never persisted, so `MediaDashDb.GetRepairSummary` had shipped as a stub returning zeros. Repair rows written from this build onwards carry the pre-repair file size; earlier repair rows are counted but not sized (footer on the panel discloses this). Panel hides on `CountLifetime == 0` so a user who has never hit a broken file sees nothing. 15 new tests cover the `ParseRepairRungLabel` parser (five known rungs + nested-paren for the coerce label + unknown-bucketed-as-other) and the aggregation query (empty history, per-rung sums within/without window, dry-run + failure rows excluded).
- Added a minimum-worthwhile-savings gate for Quality re-encodes (Settings → Files wasting space → Minimum savings %/MB). A Quality fix whose output misses the threshold is skipped and the original is kept; skipped items are terminal so the queue does not re-attempt an identical encode. Existing larger-than-original rejection is folded into the same gate. Repair and compatibility conversions are unaffected. (roadmap i-110-minimum-savings)
- Added Playability repair rung 4a — audio-only re-encode — between "Change container to MKV" and "Re-encode video". Fires only when a file's single audio track is broken and video decodes cleanly (previously rung 2 refused because dropping the only audio would leave zero audio streams, and rung 4 was the only remaining option). Video is copied so this completes in minutes instead of hours; source container and file extension are preserved so Jellyfin watch history is not reset. Toggle in Settings → Repair broken files; default on. (roadmap i-bl-12-rung4a-audio-reencode)
- Added persistent Never-modify protection for folders and libraries. Settings → Protected paths lets you register a folder (absolute path) or a Jellyfin library and choose which scanners and which fixers are blocked at that location: leave a mask empty to allow that phase, use `*` to block everything, or list IssueType names (e.g. `Quality,Duplicate`) to block only those. Protection is enforced both at scan time (no issues are recorded for a protected path) and at fix time (queued issues that pre-date the rule are silently skipped and remain visible so removing protection later resumes them). Rules survive plugin restarts (new SQLite table `protection_rules`, schema v8). Scoped to folders and libraries in this build; per-title and per-collection protection remains open on the roadmap. (roadmap i-110-protected-media)
- Extended the ffmpeg hardware-decode whitelist to `mpeg2video` and `vc1`. Legacy MPEG-2 / VC-1 sources now use the same GPU-resident decode → GPU-scale → GPU-encode pipeline as h264/hevc/vp9/av1 on NVENC / QSV / VAAPI encoders, cutting CPU time significantly on Blu-ray remuxes and older DVR captures. mpeg4 (DivX/XviD) stays off the whitelist because ffmpeg's mpeg4 HW decoder is spotty across GPU families; SW-decode + HW-encode remains the fallback. (roadmap i-bl-02)
- Overview now surfaces the current file's own progress alongside the queue-wide "N of M items left" — during a re-encode you see the running file's ffmpeg percentage tick from 0 to 100 %, not just the file count. Only shown for fixers that actually report a per-file signal (Transcode / Playability repair via ffmpeg's `-progress` pipe); light fixers stay silent instead of faking a bar. (roadmap 3f821f32-bb56-4708-9ba9-fbb7e6906c35)
- Added a dismissible low-space warning banner on Overview for library, recycle-bin and plugin-data drives. Fires when any monitored drive crosses the configured % used threshold (Settings → Safety → Low disk space; default 90 %). ZFS and Btrfs auto-tighten by 5 % because their allocators fragment sooner as free extents shrink. Advisory only — never blocks fixes; the recycle-bin cap still owns the hard stop. Per-drive dismissal lasts 7 days in the browser. (roadmap i-bl-11-space-cliff-warning)
- Stabilisation sweep for the 1.0.8.0 release closed out. Test suite at 1287/1287, playability repair audit complete across rounds R01–R10, and the CHANGELOG/README/PLAN reconciliation completed; the still-unshipped subtitle-extract feature remains scoped to 1.3.0.0. (roadmap i-176-pre-release-sweep)
- Added a CI smoke workflow (`.github/workflows/smoke.yaml`) that builds the plugin, launches an actual Jellyfin container against both supported host lines (10.11.x and 12.x) and asserts the plugin loads without throwing a load-time exception. Runs on every push and PR; complements the existing unit and harness self-tests without needing library fixtures. (roadmap i-108-cross-platform-verification)
- Overview now explains a "0 fixed" fix-run outcome instead of leaving it silent. The "Last fix run" summary (`FixRunSummary.SkippedLibraryDisabled`) records how many queued items were skipped because their library isn't currently enabled in Settings → Libraries, and a dismissible banner offers a one-click "Clear stale queued items" that dismisses them (recoverable from the Issues tab via Revert). Previously that "N skipped" number lived only in the Jellyfin log, so a user hitting Run fixes on a queue full of stale items saw nothing change on disk and no on-page explanation.
- Fixed a "ghost items keep coming back after fix" loop where MediaDash removed a file (Playability recycle, Duplicate recycle, etc.), then the next scan re-flagged the same path as a new Playability issue because Jellyfin's library database still had the item row pointing at the (now missing) file. `PlayabilityFixer` and `DuplicateFixer` now call `ILibraryManager.DeleteItem` synchronously after a successful disposal so the Jellyfin item row is purged in the same fix run — previously this was left to `ILibraryMonitor.ReportFileSystemChanged`'s async debounce, whose pending batch is lost on any Jellyfin restart. Additionally: `PlayabilityFixer` now handles the "file already gone" branch by actively reaping the ghost item and reporting a real success (previously it reported a soft `SourceMissing` failure with no cleanup, so the ghost was re-detected on every rescan).
- Fixed a 0-byte file being stuck in the Playability queue forever with no way to remove it via the UI. `PlayabilityFixer.RevalidateAsync` now checks for an empty file BEFORE calling ffprobe, so the "file is unambiguously broken → disposal path" runs even when this build's ffprobe returns a non-null error-stub for a 0-byte input (previous 0-byte guard only fired on a null probe). Field-report 2026-09-25: `Zero Byte (2026).mkv` retried every fix run with "Can't safely check this file right now — ffprobe didn't respond", hiding the fact that ffprobe was working fine — it just had nothing to parse.
- Issues tab now shows per-row "Last attempt failed: X (timestamp)" on Queued items that MediaDash has already tried and failed. Same for the row's action-hint chip, which flips from "Queued for next fix run" to "Retry on next fix run — the last attempt failed" so a user browsing the queue can tell at a glance which items are still pending vs stuck in a retry loop (e.g. `MissingSubtitles` rows where no provider has a matching subtitle). Powered by a new `HistoryStore.GetLatestAttemptsByIssueIds` batch lookup — one query per Issues-tab page load, keyed by issue id, so a page of 500 rows still costs one round-trip.

Characterization added in `tools/comprehensive-test/ui-lifecycle-self-tests.js` as a `createInlineDirtyTracker` factory that documents the `shouldApplyServerConfig` contract (7 new assertions).

The row's `SuggestedFix` and `DetailsJson` are baked at scan time, so any config field a scanner reads is stale in the DB the moment the user changes it. Fix (three-part): (1) new `Configuration/ConfigChangeInvalidation.cs` maps each `PluginConfiguration` property to the `IssueType`(s) whose Detected rows go stale when the property changes — language allowlists, quality ceilings, duplicate confidence knobs, target paths, orphan-scan toggles, and every per-type `FixMode`; `EnabledLibraries` is a full-rescan sentinel. (2) new `ScheduledTasks/ConfigChangeRescanner.cs` (IHostedService) subscribes to `BasePlugin<PluginConfiguration>.ConfigurationChanged`, holds a snapshot of the last-seen config, diffs on every save via reflection, wipes Detected rows for the affected types via a new `MediaDashDb.WipeDetectedForTypes(...)` (Queued / Dismissed rows are preserved so the user's approval / suppression outlives a config edit), then schedules a debounced (750 ms) targeted rescan via a new `ScanTask.NextRunTypeFilter` static that narrows the run to just the affected scanners. Belt-and-braces: (3) the configPage.html "Scan now" click handler now autosaves the settings form first if it's dirty and waits (up to 3s) for the save to complete before posting `/Scan`, so a user who edits chips then clicks Scan without hitting Save still gets the correct scan. 14 new tests: `ConfigChangeInvalidationTests` covers the diff (identical / array-content / scalar / enum / same-content-different-instance), the field→type map (audio language, subtitle language mapping to both `SubtitleLanguage` + `MissingSubtitles`, unrelated returning empty, `EnabledLibraries` full-rescan sentinel, target paths mapping to both `Misplaced` + `Ungrouped`), the deep-clone independence, and the exact #64 regression (`AllowedAudioLanguages` change → `AudioLanguage` only). `MediaDashDbWipeDetectedTests` covers only-given-types, Queued/Dismissed preservation, empty-set no-op, and multi-type single call. - fixed in-flight encoder/remuxer staging files being indexed as media by Jellyfin (root-cause audit 2026-09-20 R09, Medium — ghost items + potential mid-encode read-lock conflicts). Pre-fix every `TranscodeFixer.SidecarPath` output ended in a real container extension (`movie.mkv.mediadash.tmp.<token>.mp4`), so Jellyfin's real-time monitor and library-scan task treated the partial file as new media, added it as an item, then had to reconcile the ghost after MediaDash's swap-and-delete completed. On multi-user servers the ghost briefly appeared in Recently Added; on Automatic mode the MediaDash DuplicateScanner could also flag the tmp against the source and queue it, creating stale-keeper drama. Metadata-provider file opens against the partial could also race the encoder's write on Windows (shared-read → intermittent "cannot access file" ffmpeg errors that looked like disk/permission problems). Fix: `SidecarPath` now appends a `.mediaDash.tmp` non-media tail on every sidecar (middle infix `.mediadash.<marker>` preserved so `LibraryGuard.SweepOrphanSidecars` patterns still match); ffmpeg no longer infers output format from the extension, so a new `TranscodeFixer.ContainerToFfmpegFormat(container)` helper maps every known container/audio/image type to its ffmpeg `-f` muxer name (matroska, mp4, ipod, mov, avi, webm, mpegts, mpeg, flv, ogg, opus, mp3, flac, wav, adts, asf, webp, image2). Every output call site now passes `-f` explicitly: `TranscodeFixer.BuildArgs`, `TrackFixer.RunTrackRemuxAsync`, all four `PlayabilityFixer` repair rungs, both `EmbeddedCoverArtFixer` intermediates (raw PNG + webp) plus the cover-strip remux, and `MediaSorterFixer`'s cross-volume staging path (which now routes through `SidecarPath` for consistency). Recovery files (`*.mediadash-recover-*.<realExt>`) keep the real extension deliberately — those are post-encode legitimate media the user is expected to rename back if a swap failed. 8 new tests cover the tail contract (`.tmp` at end, no known media extension), sweep-pattern middle-infix regression, and 15 container→ffmpeg-format mappings including image2 fallback for png/jpg/webp/bmp.
- fixed EmbeddedCoverArtFixer, TranscodeFixer, and TrackFixer still enabling data loss under a crash between original disposal and the final rename (root-cause audit 2026-09-19 R02+R03, Critical under permanent disposal). The 1.0.7.8 P-01/P-02/P-03 fixes made the reactive `SwapRecoveryHelper.TryPreserve` sound and wired it into cover-art too — but the helper only ran from the fixer's finally block, so a process kill (SIGKILL, container OOM, hard power loss) between `originalDisposed = true` and the final `File.Move(swapPath, target)` left the only remaining copy at a sweep-doomed `.mediadash.swap` / `.mediadash.new.<token>` path — the next fix cycle's `LibraryGuard.SweepOrphanSidecars` matched the pattern and deleted it. The reactive helper's own total-failure branch also returned the sweep-doomed path, so a File.Copy fallback failure produced the same outcome via a different mechanism. Fix: new `SwapRecoveryHelper.TryPromoteBeforeDispose(swap, original, out recovery)` renames the verified swap to a `.mediadash-recover-*` name OUTSIDE every sweep pattern set BEFORE the caller disposes the original. All three fixers gain the promote-before-dispose call and abort with `FixResult.Fail` on `false` — original stays intact, the leftover swap gets swept safely next cycle because the original is still present to prove disposability. Final rename uses the recovery path instead of the swap path, so a subsequent crash still finds the file outside every sweep pattern via the existing `IsRecoveryCopy` skip. Removed the `originalDisposed` flag from all three fixers (recoveryPath presence is the new signal) and the reactive `TryPreserve` calls in the finally blocks (obsolete — promote is now proactive pre-dispose). 5 new tests cover happy-path promote, source-missing abort, long-UTF8-basename hash fallback (the R03 244-byte case), directory-collision suffix, and the promote→sweep-pattern contract.
- fixed DuplicateFixer accepting a keeper that had been truncated to 0 bytes (or materially shrunk) between scan and fix, then deleting the nonempty loser in its favour (root-cause audit 2026-09-19 R07, High — destructive under permanent disposal). Fix-time validation checked `File.Exists(keeperPath)` but never re-measured the file — the scanner's ranking premise ("this keeper is the better copy") went stale by execution time. Fix: new `DuplicateFixer.KeeperStillViable(keeperPath, detailsJson, out reason)` static — refuses when current keeper size is 0 bytes OR (when DetailsJson.keeper.Size was recorded > 0 at scan time) has dropped below half. Refusal message names the size delta so the user can decide to re-scan or investigate what truncated the file. Pure and testable: file existence + FileInfo.Length only, no probe/hash/library dependency. 6 new tests cover 0-byte, half-size-truncation, healthy same-size regression guard, missing scan-time-size fallback, missing keeper file, and malformed DetailsJson defence.
- fixed MediaGrouperScanner returning the wrong Series folder for TV reboots whose year suffix is followed by a bracketed provider tag (root-cause audit 2026-09-19 R08, High — silent wrong-metadata group). `SeriesYearSuffixRegex` was anchored to end-of-string (`^(.+?)\s*\((\d{4})\)\s*$`), so `Doctor Who (1963) [tvdbid-76107]` failed to match — `FindYearSuffixedSeriesFolder` returned null and Rule 2 synthesised `Doctor Who (2005)` from Jellyfin's (wrong, TVDb-collapsed) reboot-year metadata. Same symptom class as the movie-side same-title-different-year fix earlier in 1.0.7.8, but for the TV series-folder branch, and specifically for users who pin the correct provider ID on their reboot folders to prevent Jellyfin from collapsing them. Fix: regex extended to `^(.+?)\s*\((\d{4})\)(?:\s*\[[^\]]+\])*\s*$` — tolerates 0+ trailing bracketed provider tags, so `Doctor Who (1963) [tvdbid-76107]`, `Silo (2023) [imdbid-tt14688458]`, and multi-tag `Doctor Who (1963) [tvdbid-76107] [imdbid-tt0056751]` all keep the on-disk year the user explicitly recorded. 6 new tests cover single-tag (TVDb / TMDb / IMDb), multi-tag, plain-year regression guard, and tag-without-year defence (correctly falls through to Rule 2 for `Doctor Who [tvdbid-76107]` without leading year).
- fixed RestoreOptimizedCopy endpoint never marking the restored path as auto-fix-vetoed (root-cause audit 2026-09-19 R04 sibling). Peer restore endpoints (RestoreFromHistory, RestoreByBinPath, batch RestoreOneBinPath) all record the restored path in `restored_paths` after 1.0.7.8's P-04 fix, so the next scan's auto-queue skip fires; RestoreOptimizedCopy was the miss. A user regretting a Quality re-encode and clicking Restore on the original would silently see it re-transcoded within one auto-queue cycle. Fix: added `_db.MarkPathRestored(entry.Path, entry.Type)` symmetrically to the peers, after `AcknowledgeHistoryEntry`.

- fixed Track fix (audio / subtitle language cleanup) failing with a raw `ffmpeg failed on '<file>': [ipod @ ...] Tag text incompatible with output codec id '98314'` diagnostic when the source was an MP4-family file (`.m4v`, `.mp4`, `.m4a`, `.mov`) carrying bitmap subtitles — VobSub, PGS, or DVB (codec `98314` is VobSub). The mp4/ipod muxer refuses those subtitle codecs under `-c copy`, so the whole remux exited non-zero and the pre-fix file was left untouched (GitHub #56, reported by @fadern for HandBrake-encoded `TaleSpin (1990)/…m4v` files with a Danish VobSub track). TrackFixer's remux now folds any MP4-muxer-incompatible subtitle stream into the same negative-map list it already builds for wrong-language tracks, so the fix succeeds and the History-tab row spells out what was dropped ("… Also dropped 1 bitmap subtitle track the .m4v container cannot hold under -c copy."). Fires only when the target extension is MP4-family AND the source has a genuinely incompatible bitmap sub; MKV / M2TS / TS remuxes pass through unchanged, and text subs (subrip, ass, mov_text) are never dropped. 6 unit tests cover the codec / extension matrix.
- fixed the Repair broken files ladder never getting past rung 1 or rung 2 for any `.mkv` source — every `.mkv` file whose repair required rung 3 (container coerce) or rung 4 (video re-encode) silently fell through to delete instead of being salvaged. The `TrySwapRepairedAsync` collision guard was comparing the extension-changed target path against `File.Exists(finalPath)` without accounting for `Path.ChangeExtension(x.mkv, ".mkv")` being a no-op — the "collision" it detected was the source file itself, still on disk pre-recycle. Fix computes `pathActuallyChanged = extensionChanged && !string.Equals(finalPath, issue.Path)` and only applies the collision guard + the library-monitor double-notify when the extension truly changes. Rung 4 on `.mkv` sources (the most common repair path for bit-flip damage) now works instead of always deleting.
- fixed rung 1 (quick remux) producing outputs that failed strict decode on any file with tail-truncation damage — MP4/M4V downloads interrupted mid-transfer had a partial AAC packet at the tail that `-c copy` copied through, then the AAC decoder choked on the incomplete tail and Jellyfin refused to direct-play the "repaired" file. Added `+discardcorrupt` to the `-fflags` on all three repair ffmpeg calls (rungs 1, 3, 4); the demuxer now drops the trailing partial packet at read time so the remux writes a clean container terminating at the last complete packet. No effect on whole files or MKVs where the packet boundary was already clean.
- added `tools/repair-test/torture-test.ps1` — real-file end-to-end test that downloads a Big Buck Bunny clip and breaks it 15 different ways (MP4 / MKV / FLV / AVI tail truncations at various sizes, mid-file XOR bit-rot at 0.5–8 %, zeroed regions, 100 scattered byte flips, EBML head damage, moov-only-4KB stubs, extension-lied files, doubled damage), then runs the whole scan + fix loop against a live Jellyfin and verifies every output either plays end-to-end under `-xerror` OR was safely recycled with the original preserved. 15/15 handled correctly on the current build in ~21 s of fix work — including 8 % XOR damage on real 720p H264 that rung 4 re-encodes cleanly.
- reworked the `tools/repair-test/` fixture suite to actually test what real users hit. Nine broken fixtures now cover: MKV tail truncation (128 KB + 100 KB), MP4 with intact faststart moov + 400 KB tail truncation, two-audio MKV with one broken track, MPEG-4 in AVI + tail truncation (fixture name is legacy — HEVC-in-AVI was untestable because ffmpeg mis-identifies HEVC packets as rawvideo), H264 in FLV + tail truncation, and two mid-file bitstream XOR variants (2%, 5%). Every broken fixture ends the run with a strict-`-xerror`-decodable output somewhere on disk (either its original name if rung 1/2 handled it, or the `.mkv` variant if rung 3/4 did) — the "would Jellyfin actually play the repaired file?" gate is now enforced. `validate-fixtures.ps1` mirrors the plugin's scanner (exit-code OR 90 % shortfall) instead of the stricter `-err_detect explode` alone. `validate-outputs.ps1` accepts whichever rung succeeded first (semantic bar is "playable output exists" not "specific rung fired"). Retired `rung2-broken-sub.mkv` — isolating a broken-subtitle-only scanner trigger is unrealistic and `rung2-broken-second-audio.mkv` already covers rung 2's drop-broken-stream flow. 9/9 fixtures end-to-end through a live Jellyfin at localhost:8099 in ~8 s of fix work.
- fixed the four Repair broken files checkboxes (Settings → Files that won't play → Repair broken files) rendering unchecked on first render. If the Settings page was ever Save-submitted before the load pass reached those inputs, all four flags got persisted as `false` — which silently disabled the whole repair ladder and every unplayable file went straight to delete without a rescue attempt, no visible indication anywhere. Initial checkbox HTML now defaults `checked` so a race can never bake in the off state. Existing users whose config was persisted as `false` need to re-tick the boxes in Settings (or delete the four `<RepairAttempt…>` lines from `plugins/configurations/Jellyfin.Plugin.MediaDash.xml` and restart — the constructor defaults will apply cleanly).
